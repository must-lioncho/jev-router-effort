# Jev Router Q&A

[English (default)](QNA.md)

## Q1. Jev에 보내는 모델 선택 프롬프트는 무엇인가?

`src/config.mjs`의 `questionForModels()`가 다음 두 지시를 만듭니다.

> Pick the cheapest exact model that can fully complete this coding request in one pass, without retrying on a stronger model.
>
> Treat different model versions as separate choices. Judge required reasoning, not requested reply length.

뜻은 다음과 같습니다.

> 이 코딩 요청을 더 강한 모델로 재시도하지 않고 한 번에 완수할 수 있는, 가장 저렴한 정확한 모델을 고른다. 모델 버전은 서로 다른 선택지로 취급하며, 답변 길이가 아니라 필요한 추론 수준으로 판단한다.

이 지시와 함께 현재 로그인한 계정 및 CLI에서 실제로 사용할 수 있는 모델 ID 목록을 선택지로 보냅니다. 각 선택지에는 해당 모델의 티어에 맞는 용도, 적합 신호, 부적합 작업 설명도 붙습니다. 따라서 Jev가 임의의 숫자를 모델명으로 변환하는 구조가 아니라, 제공된 **정확한 모델 ID 중 하나를 직접 고르는 구조**입니다.

`src/router.mjs`의 `askJev()`는 사용자 요청 원문 외에도 현재 모델, 대략적인 대화 컨텍스트 토큰 수, 사용 가능한 모델 ID를 상태 정보로 보냅니다.

## Q2. Jev 응답에는 무엇이 들어오는가?

핵심 모델 선택 응답에는 다음 값이 들어옵니다.

- `choice`: Jev가 추천한 정확한 모델 ID
- `confidence`: 그 추천에 대한 Jev의 확신도
- `probabilities`: 각 선택지에 대한 확률 정보

모델 선택과 별도로 다음 세 항목을 0~9 척도로 질문하고, 라우터는 이를 0~1 값으로 정규화해 `metrics`에 보관합니다.

- `taskComplexity`: 요청의 모호성, 범위, 영향 범위를 포함한 전체 작업 복잡도
- `reasoningRequired`: 요청을 한 번에 정확히 끝내는 데 필요한 추론량
- `toolComplexity`: 도구가 없거나 단순한 경우부터 여러 상태성 도구를 조율하는 경우까지의 도구 사용 복잡도

여기에 컨텍스트 사용 비율인 `contextSize`도 로컬에서 계산합니다. 중요한 점은 이 복잡도 점수들을 코드가 합산해 모델 티어를 산출하지 않는다는 것입니다. **모델 추천은 `choice`가 직접 나타내고, 별도 점수들은 설명과 관찰을 위한 지표**입니다.

또한 `confidence`는 “이 모델이 작업에 성공할 객관적 확률”로 보정된 수치라고 코드가 보장하지 않습니다. 정책은 이를 Jev 추천의 불확실성을 나타내는 신호로 사용합니다.

## Q3. Jev AI가 라우팅을 최종 결정하는가?

아니요. 다만 “Jev는 결정하지 않는다”라고만 표현하면 역할을 지나치게 축소하게 됩니다.

- **Jev**는 사용 가능한 정확한 모델 ID 중 후보 하나를 추천하고 확신도와 평가 점수를 반환합니다.
- **`src/router.mjs`**는 Jev에 보낼 요청을 조립하고 호출합니다. 성공하면 응답을 정리하고, 실패·타임아웃이면 `null`을 반환합니다. 이 파일 자체가 최종 정책을 판정하지는 않습니다.
- **프록시(`src/proxy.mjs`, `src/codex-proxy.mjs`)**는 Jev가 고른 정확한 모델 ID를 공통 티어로 변환해 정책에 넘긴 뒤, 정책 결과를 실제 모델 ID로 확정해 요청에 적용합니다.
- **`src/policy.mjs`**의 `decide()`가 사용자 우선권, 낮은 확신도, 사용 가능 여부, 캐시 비용 같은 코드 규칙을 적용해 최종 실행 티어를 확정합니다.

따라서 정확한 설명은 **“Jev가 모델 후보를 추천하고, 코드 정책이 그 추천을 수락·제한·거부해 최종 실행 모델을 확정한다”**입니다.

## Q4. 최종 의사결정의 우선순위와 예외 규칙은 무엇인가?

우선순위는 다음과 같습니다.

1. 사용자가 `/model`에서 `jev-router`가 아닌 구체적인 모델을 선택하면 프록시는 Jev 라우팅을 건너뛰고 그대로 전달합니다. 이것이 가장 바깥쪽의 최우선 사용자 선택입니다.
2. 자동 라우팅 중에도 요청 원문에 `use opus`, `use luna`, `use strong`처럼 지원되는 명시적 모델·티어 지시가 있으면 `src/policy.mjs`의 override가 Jev 추천보다 우선합니다.
3. Jev 호출이 실패하거나, 타임아웃되거나, 응답이 없거나, 추천 모델이 현재 후보 목록에 없으면 현재 모델을 유지합니다.
4. `confidence < 0.3`이면 현재 모델보다 약한 티어로 내리지 않습니다. 더 강한 티어 추천도 현재 티어와 balanced 티어 중 더 높은 곳까지만 허용합니다. 즉 현재가 이미 strong이면 억지로 balanced로 내리지는 않습니다.
5. 현재보다 약한 티어로 내리는 추천이라도 대화 컨텍스트가 20,000토큰을 넘으면 모델 전환에 따른 프롬프트 캐시 재생성 비용 때문에 현재 모델을 유지합니다.
6. 결정된 티어가 계정에서 사용할 수 없으면 가능한 한 바로 위의 더 강한 티어를 선택합니다. 위 티어가 없을 때만 아래 티어를 선택합니다. 추가 사용량 비용이 드는 `fable`은 원래부터 `fable`이 요청된 경우가 아니면 자동 상향 대상으로 삼지 않습니다.
7. `fable` 티어 자체도 `JEV_ALLOW_FABLE=1`일 때만 자동 라우팅 후보에 포함됩니다.

Jev의 정확한 모델 추천이 정책에 의해 그대로 수락되면 그 버전의 모델 ID를 실행합니다. 정책이 추천을 제한하거나 다른 티어로 바꾸면 프록시가 해당 티어의 적절한 모델 ID를 골라 실행합니다.

## Q5. 어느 파일이 최상위 의사결정 소스인가?

한 파일이 모든 층에서 무조건 최상위인 구조는 아닙니다. 책임별 정본(source of truth)은 다음과 같습니다.

| 파일 | 정본으로 관리하는 내용 |
| --- | --- |
| `src/config.mjs` | 티어 순서, 기본 모델 ID, Jev 질문, 티어별 가이드, 확신도·컨텍스트·타임아웃 임계값, 명시적 override 패턴 |
| `src/router.mjs` | Jev 요청 형식, 호출·타임아웃·재시도, 응답 및 관찰 지표 정규화 |
| `src/policy.mjs` | Jev 추천을 받아 최종 티어를 확정하는 순수 정책과 예외 처리 |
| `src/proxy.mjs` | Claude Code에서 사용자 수동 선택 우선 처리, 실제 계정 모델 카탈로그와 정책 결과를 최종 Claude 모델 ID에 연결 |
| `src/codex-proxy.mjs` | Codex에서 실제 계정 모델 카탈로그와 정책 결과를 최종 Codex 모델 ID에 연결 |

정책 규칙의 최상위 소스는 `src/policy.mjs`이고, 정책에 쓰이는 설정값의 최상위 소스는 `src/config.mjs`입니다. 그러나 실제로 어떤 모델 ID가 실행되는지는 프록시가 계정의 실시간 모델 카탈로그와 정책 결과를 함께 보고 확정합니다. 따라서 전체 흐름은 다음과 같습니다.

```text
사용자의 구체적 수동 모델 선택
  └─ 있으면 그대로 통과
  └─ 없으면 Jev가 정확한 모델 ID 추천
       └─ policy가 override·confidence·context·availability 규칙 적용
            └─ proxy가 최종 티어를 실제 모델 ID로 확정해 실행
```

이 구조 덕분에 AI 추천이 비정상적이거나 불확실하거나 사용할 수 없는 모델을 가리켜도, 코드에 적힌 결정적 안전 규칙이 실행 모델을 통제합니다.

## Q6. `src/config.mjs`의 Claude 모델 ID를 Opus 5.5로 버전업해야 하는가?

**결론부터 말하면, 정상 라우팅을 위해 반드시 즉시 바꿔야 하는 것은 아니지만 cold start 복원력을 위해 업데이트하는 것이 권장됩니다.**

정상적인 Claude 경로에서는 프록시가 `GET /v1/models`로 로그인한 계정의 모델 카탈로그를 받아 실제 후보 목록을 만듭니다. Jev에는 이 카탈로그에 들어 있는 정확한 모델 ID가 선택지로 전달됩니다. 따라서 `src/config.mjs`의 정적 기본값이 `claude-opus-5`여도 계정 카탈로그에 `claude-opus-5-5`가 있으면 Jev는 `claude-opus-5-5`를 정확한 후보로 추천할 수 있고, 정책이 그 추천을 수락하면 그대로 실행할 수 있습니다.

즉, 정상 경로에서 `TIERS`의 정적 ID는 최신 모델 목록의 정본이 아닙니다. 실제 계정 카탈로그가 정본에 가깝고, 모델 버전별 선택도 그 카탈로그를 기준으로 이뤄집니다.

다만 카탈로그가 아직 없거나 비어 있는 cold start 경로에서는 `TIERS`의 정적 ID가 실제 fallback이 됩니다. 이때 정적 ID가 오래되어 더 이상 실행되지 않거나 계정에서 제공되지 않으면 첫 요청의 복원력이 떨어질 수 있습니다. 그러므로 Opus 5.5가 공식 API와 해당 계정에서 실제 제공되는 것을 확인했다면 정적 fallback도 그 유효한 ID로 갱신하는 편이 안전합니다.

권장 개선 순서는 다음과 같습니다.

1. 첫 generation 요청을 전달하기 전에 모델 카탈로그를 먼저 가져와 검증합니다.
2. 같은 티어에 여러 버전이 있으면 Anthropic Models API의 `created_at` 같은 명시적 메타데이터로 최신 모델을 정렬·선택합니다. 이름 문자열의 사전식 비교에 의존하지 않습니다.
3. 카탈로그가 없을 때는 검증되지 않은 정적 모델 ID를 곧바로 실행하지 않습니다. 카탈로그 확보를 재시도하거나, 검증된 마지막 카탈로그를 사용하거나, 명확한 오류로 중단합니다.
4. 정적 ID를 유지한다면 정상 라우팅의 주 후보가 아니라 비상 fallback으로 취급하고, 공식 모델 목록에 맞춰 주기적으로 갱신합니다.

이렇게 하면 단순히 `opus-5`를 `opus-5-5`로 한 번 바꾸는 것보다 새 모델 출시 때마다 같은 문제가 반복되는 것을 더 근본적으로 막을 수 있습니다.
